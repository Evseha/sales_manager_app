# Техническое задание: AI Product Assistant

**Версия:** 1.0  
**Назначение:** тестовый прототип сервиса для подготовки B2B товарных описаний контрольно-измерительных приборов и промышленного оборудования.  
**Среда разработки:** PyCharm, Python 3.12+.

---

## 1. Цель проекта

Разработать локальное веб-приложение AI Product Assistant. Пользователь передаёт исходные сведения о товаре (название, модель, производителя, технические характеристики, описание, паспортные данные и/или URL страницы товара), а приложение формирует структурированную товарную карточку для B2B-каталога.

Приложение должно использовать LLM как инструмент подготовки и структурирования текста, но не должно придумывать технические характеристики или выдавать предположения за подтверждённые факты.

## 2. Тестовые товары

Для демонстрации предусмотреть два тестовых примера:

1. ОВЕН БП15Б-Д2 — https://www.souz-pribor.ru/product/bp15b-d2/
2. ОВЕН БП120Б-Д9-24С — https://www.souz-pribor.ru/product/bp120b-d9-24s/

Названия и ссылки являются входными идентификаторами тестовых примеров, а не подтверждением каких-либо технических параметров. Не зашивать в приложение неподтверждённые характеристики. Если данные извлекаются со страницы, сохранять исходный текст/значения и URL-источник. Если страница недоступна или содержит недостаточно данных, явно сообщить об этом пользователю.

## 3. Результат генерации

Для каждого товара приложение формирует пять блоков.

### 3.1. SEO-заголовок
- Максимум 70 символов, включая пробелы.
- Содержит тип товара, производителя и модель, если эти сведения есть во входных данных.
- Не содержит неподтверждённых обещаний и характеристик.

### 3.2. SEO-описание
- Целевой объём: 800–1200 символов с пробелами.
- Стиль: профессиональный B2B, ясный, технически корректный, без рекламных преувеличений.
- Описывает назначение, особенности и области применения только в пределах подтверждённых данных.
- Не добавляет отсутствующие параметры, сертификаты, совместимость, степень защиты, диапазоны, материалы или комплектацию.
- Если достоверных сведений недостаточно для целевого объёма, не заполняет объём выдуманным текстом: выводит более короткий текст и предупреждение о недостаточности исходных данных.

### 3.3. Таблица технических характеристик
Для каждой характеристики предусмотреть:
- наименование параметра;
- значение;
- единицу измерения (если указана);
- исходную формулировку/значение;
- источник (поле ввода, документ, URL и, если доступно, фрагмент страницы);
- статус достоверности: `подтверждено`, `требует проверки`, `данных нет`.

Числа, диапазоны, знаки, обозначения и единицы измерения сохранять точно. Не выполнять автоматическую конвертацию единиц и не округлять значения.

### 3.4. Поисковые запросы
- Сформировать 3–5 релевантных поисковых запросов.
- Использовать подтверждённые название, модель, производителя, тип оборудования и назначение.
- Не добавлять неподтверждённые технические параметры в запросы.

### 3.5. Коммерческий блок для менеджера
Кратко сформировать:
- кому может подойти товар;
- какие задачи он может решать;
- где может применяться.

Каждое утверждение должно опираться на входные сведения. Если назначение или область применения не подтверждены, прямо указать, что требуется уточнение по документации производителя.

## 4. Принципы достоверности и ограничения AI

Это обязательные требования.

1. Запрещено придумывать технические характеристики, числовые значения, единицы измерения, сертификаты, допуски, совместимость, комплектацию и условия эксплуатации.
2. Если значение отсутствует, выводить `Данных нет`.
3. Если источники противоречат друг другу, не выбирать значение самостоятельно. Показать оба варианта, указать источники и пометить параметр `требует проверки`.
4. Не исправлять и не нормализовать исходные обозначения моделей, артикулов и параметров без отдельного поля для нормализованного значения.
5. Не выполнять пересчёт единиц, округление и вывод новых технических значений.
6. Разделять факты из источника и маркетинговую формулировку. Текст описания должен быть составлен только из фактов, прошедших проверку.
7. Сохранять исходные данные отдельно от сгенерированного текста.
8. Для каждого извлечённого факта сохранять источник/происхождение, если он доступен.
9. Пользователь должен иметь возможность отредактировать входные данные и повторно запустить генерацию.
10. AI-ответ не считается проверкой соответствия товара нормативам или инженерным требованиям.

## 5. Функциональные требования

### 5.1. Ввод данных
Реализовать в интерфейсе:
- ручной ввод названия товара;
- ввод производителя и модели;
- ввод краткого описания;
- ввод технических характеристик в виде структурированного списка или JSON;
- большое текстовое поле для вставки текста паспорта/руководства/каталога;
- загрузку JSON-файла с исходными данными;
- поле URL страницы товара для дополнительного извлечения информации.

Все способы ввода должны быть необязательными по отдельности, но перед генерацией приложение должно проверить, что есть хотя бы один содержательный источник данных.

### 5.2. Извлечение со страницы URL
Реализовать как дополнительную возможность, не как единственный источник данных:
- получать страницу через `requests` с таймаутом;
- разбирать HTML через BeautifulSoup;
- извлекать заголовок, мета-описание и видимый текст основной части страницы;
- не обходить авторизацию, CAPTCHA, paywall и технические ограничения сайта;
- показывать пользователю, что именно удалось извлечь;
- не считать текст страницы автоматически подтверждённой спецификацией, если структура источника не позволяет установить это;
- при ошибке сети, HTTP-ошибке или пустом содержимом показывать понятное сообщение и позволять продолжить с ручными данными.

Не выполнять массовый сбор страниц. Соблюдать ограничения сайта и применимое законодательство.

### 5.3. Генерация через Gemini
- Использовать официальный пакет `google-genai`.
- API-ключ получать только из переменной окружения `GEMINI_API_KEY`.
- Модель задавать через `GEMINI_MODEL` в `.env`, чтобы её можно было менять без правки кода.
- Использовать структурированный JSON-ответ, соответствующий Pydantic-модели.
- Не хранить ключ в исходном коде, Git, логах или пользовательском интерфейсе.
- При отсутствии ключа показывать инструкцию по настройке `.env`.
- При ошибке API, ограничении частоты запросов, таймауте или некорректном ответе показывать понятную ошибку и не терять введённые данные.

### 5.4. Проверка результата
Выполнять программную проверку после ответа модели:
- наличие всех пяти блоков;
- SEO-заголовок не превышает 70 символов;
- SEO-описание: проверка длины 800–1200 символов; если короче из-за нехватки фактов, выводить предупреждение, а не дополнять выдумками;
- поисковых запросов от 3 до 5;
- у характеристик заполнены обязательные поля модели данных;
- отсутствующие значения обозначены `Данных нет` либо явно отсутствуют с соответствующим статусом;
- значения и единицы измерения не преобразуются программой;
- JSON корректно разбирается и проходит Pydantic-валидацию.

Проверка не должна объявлять технический факт истинным только потому, что его вернула LLM. Отображать источники и статусы проверки.

### 5.5. Редактирование
Пользователь должен иметь возможность:
- редактировать исходные поля;
- исправлять сгенерированные текстовые блоки;
- редактировать таблицу характеристик;
- повторно генерировать карточку;
- копировать каждый блок отдельно.

### 5.6. Экспорт
Реализовать экспорт карточки:
- JSON — структурированный результат;
- Markdown — карточка с заголовками и таблицей;
- TXT — простой текстовый вариант.

Имя файла формировать на основе модели/названия товара безопасным способом. Не перезаписывать файлы без явного выбора пользователя. Экспортировать также исходные данные и сведения об источниках, если они есть.

## 6. Интерфейс

Использовать Streamlit. Интерфейс должен быть простым, аккуратным и преимущественно серым/нейтральным по цветовой гамме.

Предлагаемая компоновка:
1. Заголовок `AI Product Assistant`.
2. Боковая панель или верхний блок ввода товара.
3. Вкладки/секции: `Исходные данные`, `Извлечённые сведения`, `Результат`, `Источники и предупреждения`.
4. Кнопка `Сформировать товарную карточку`.
5. Кнопки экспорта JSON / Markdown / TXT.
6. Индикатор выполнения и понятные сообщения об ошибках.

Не скрывать предупреждения о неполных или противоречивых данных.

## 7. Технологический стек

- Python 3.12 или новее.
- Streamlit — веб-интерфейс.
- `google-genai` — Gemini API.
- Pydantic v2 — модели и валидация.

## 9. Модели данных

Создать Pydantic-модели как минимум для следующих сущностей.

### ProductInput
- `product_name: str | None`
- `manufacturer: str | None`
- `model: str | None`
- `short_description: str | None`
- `specifications: list[SpecificationInput]`
- `source_text: str | None`
- `source_url: str | None`

### SpecificationInput
- `name: str`
- `value: str | None`
- `unit: str | None`
- `source: str | None`

### SpecificationOutput
- `parameter: str`
- `value: str`
- `unit: str | None`
- `original_text: str | None`
- `source_reference: str | None`
- `status: Literal["подтверждено", "требует проверки", "данных нет"]`

### ProductCard
- `seo_title: str`
- `seo_description: str`
- `specifications: list[SpecificationOutput]`
- `search_queries: list[str]`
- `sales_block: SalesBlock`
- `warnings: list[str]`
- `sources: list[SourceReference]`

### SalesBlock
- `target_audience: str`
- `tasks: str`
- `applications: str`

### SourceReference
- `source_type: str`
- `source_name: str`
- `source_url: str | None`
- `extracted_at: str | None`

Имена полей можно расширить, но нельзя удалять сведения, необходимые для прослеживаемости.

## 10. Системная инструкция для модели

Создать отдельный файл `prompts/product_card_prompt.py` с системной инструкцией, эквивалентной следующей:

> Ты — помощник по подготовке B2B-карточек промышленного оборудования. Работай только с предоставленными входными данными и извлечёнными источниками. Не используй знания из памяти модели для заполнения отсутствующих характеристик. Не выдумывай числа, единицы измерения, диапазоны, материалы, сертификаты, степень защиты, совместимость, комплектацию и условия эксплуатации. Сохраняй исходные числовые значения, знаки, обозначения и единицы измерения без преобразования. Если сведений нет, укажи «Данных нет». Если источники противоречат друг другу или происхождение значения неясно, пометь его «требует проверки» и добавь предупреждение. Составь SEO-заголовок до 70 символов, SEO-описание целевой длиной 800–1200 символов, таблицу характеристик, 3–5 поисковых запросов и коммерческий блок. Если исходных фактов недостаточно для SEO-описания нужной длины, не выдумывай текст ради длины: верни достоверное короткое описание и предупреждение. Верни только JSON, соответствующий заданной схеме.

Промпт не заменяет программную валидацию.

## 11. Обработка ошибок

Предусмотреть обработку:
- отсутствующего или недействительного API-ключа;
- недоступности Gemini API;
- превышения лимита запросов;
- таймаута;
- пустого ответа модели;
- ответа не в JSON;
- JSON с неправильной структурой;
- недоступного URL;
- HTTP-ошибок;
- пустого или нечитаемого HTML;
- некорректного пользовательского JSON;
- отсутствия достаточных исходных данных.

Ошибки показывать понятным языком. Не выводить секреты, stack trace или API-ключ пользователю. Подробности для разработчика писать в лог без секретных значений.

## 12. Безопасность и конфигурация

Создать `.env.example`:

```dotenv
GEMINI_API_KEY=put_your_api_key_here
GEMINI_MODEL=указать_доступную_модель_Gemini
REQUEST_TIMEOUT=15
```

Файл `.env` должен находиться в `.gitignore`. Не добавлять реальный ключ в репозиторий. Проверять входные URL и обрабатывать ошибки запросов. Не выполнять содержимое загруженных файлов как код.

## 13. Тестирование

Написать автоматические тесты для:
- Pydantic-моделей и обязательных полей;
- ограничения длины SEO-заголовка;
- длины SEO-описания и предупреждения при недостатке исходных фактов;
- количества поисковых запросов;
- отсутствующих значений;
- сохранения исходных чисел и единиц измерения;
- обработки противоречивых данных;
- некорректного JSON;
- экспорта JSON/Markdown/TXT;
- ошибок при извлечении URL.

Тесты не должны требовать реального Gemini API: использовать mock/stub для API-клиента. Отдельно предусмотреть ручной smoke test с реальным ключом.

## 14. Критерии приёмки

Проект считается выполненным, если:

1. Приложение запускается локально командой `streamlit run app.py`.
2. Есть понятная форма ввода исходных данных.
3. Работают ручной ввод, вставка текста и загрузка JSON.
4. URL-извлечение работает как дополнительный источник и корректно обрабатывает ошибки.
5. Генерация обращается к Gemini через `google-genai`, используя ключ из `.env`.
6. Ответ модели разбирается и валидируется через Pydantic.
7. На экране отображаются все пять блоков товарной карточки.
8. Отображаются источники, неполные данные и предупреждения.
9. Отсутствующие сведения не заменяются выдуманными значениями.
10. Доступно редактирование результата.
11. Работает экспорт JSON, Markdown и TXT.
12. Автоматические тесты проходят.
13. В `README.md` описаны установка, настройка ключа, запуск и тестирование.
14. В репозитории нет секретов и реального API-ключа.
